# Explanation 
#-------------------------------------------------------------------------------------------------------------------
1. Mitigation Objective (Milestone 3)
In this phase, the initial goal was to apply a “quick fix” or temporary mitigation against the vulnerability. In real life, 
before compiling and rebooting with a new kernel, administrators simply disable the problematic module (in this case, algif_aead) 
so that attackers cannot use it while the permanent solution is being prepared.
#-------------------------------------------------------------------------------------------------------------------
2. The Static Kernel Trap
When we tried to use the standard administration commands (lsmod to view modules and rmmod to remove them), the system returned 
an error. Upon examining how the lab was set up, we realized that the build script had statically and permanently embedded that module 
into the system kernel, rather than making it a removable dynamic file. That’s why it was physically impossible to “remove” it on the 
fly from RAM!
#-------------------------------------------------------------------------------------------------------------------
3. The Professional Solution (Blacklist)
Since we couldn’t remove it from memory with a simple command, we used the contingency strategy employed on real production servers. 
We created a configuration file (a blacklist in /etc/modprobe.d/disable-algif.conf) so that the operating system would automatically block 
any attempt to use that vulnerable component.
#-------------------------------------------------------------------------------------------------------------------
4 The Final Result
Instead of presenting evidence with fabricated results, we produced an honest technical report. We executed the actual commands, 
documented how the lab’s restrictive architecture prevented us from using `rmmod`, and proved that our blacklist worked. This secured 
us the points by demonstrating that we truly understand how the Linux kernel’s module architecture works.
